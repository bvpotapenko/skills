/skill-creator create a skill for planning. 

I want it to be short, precise and clear, not clogging model's context, maybe better if it has sub-files a model can navigate according to current task. 



I want an agent to understand from this skill I want the agent to create the best for current task plan. 

What is the best? It really depends on the goal, priorities can be:



* fastest implementation, don't need to create 20 entities (YAGNI), optimal - use exisitng libs, instead of "inventing a bicycle again" (for example there is a known pattern "factory" - but there is already a library "python-dependency-injector", so it's better to use a library to deal with it, rather than writing own implementation; the same for reading configs there is OmegaConf and similar , there are ultra-fast and efficient solutions for message busses (subscription pattern), etc - a trusted existing sollution is better than rewriting from scratch in 9/10 cases) - run a subagent, to analyse proposed architecture, that can detect bicycle invention where it is unnecessary, and let this efficiency-subagent provide feedback on what libs can be used to simplify implementation proposed in the draft of the plan, reduce amount of code produced, makes support of the code easier.

* the most accurate calculations (when we need to evaluate something, estimate, so formulas must be addressing all variables and clear all uncertainties, nothing important should be cut off, at the same time, anything tiny that doesn't actually bring value to the result - this we omit. How to know what is important what is not: let agent directly ask me) - run a subagent to analyze math formulas, analyze logic of calculations (are all issuse were addressed, was something ignored, if was what was ignored and why), let this agent return concerns it descovered, things it noticed missing, errors in assumptions and in formulas; especially from scientific point of view: are statisticall tests fit the data we are going to work with, is math apparat we are going to apply actually fits this problem, etc -- because it's very easy to miss something when design a big thing or difficult logic, so sub-agent can help to figure it out.

* maintainability of big projects (if we write code, if we create a big project - it should scale easily, we need to follow best design principles for such systems - agent needs to clarify goals in long-term expectations of the project and address this vision in advance in a way, new features won't require re-writing of half functionality).

* Safety. What we design must address safety issues. First in terms of data (don't expose passwords, tokens), don't allow any kind of injections, always ensure there is no way for abusers (hackers) to get users' information, break into our system - code must be safe (use auth, not exposing ports for anyone, secure sql, and all other principles of safety, etc ) - run a subagent to evaluate safetiness of the plan (what is safety-ambiguous, what safety measures are "meant" but not described clear and directly, what practices are potentially dangerous, how to make it more safe -- safety-subagent returns this feedback). 

* It's also possible that all these goals above are important and we address all of them. 



How agent should approach to the plan:



1. Understand the problem user described. By understand means extract ideas and problems user describes in the request. 

2. Address to memory and current history of the project/problem (if we work on code - history of this project, if we design something and already discussed some issues - what did we discus just before, shouldn't ignore it. Also consider other requirements user defined for the agent in general.

3. Exploration. Use sub-agents to analyze and extract data. Use sub-agents to evaluate current project's code state; analyze links if user provided any; analyze literature references (pdfs, publications) with subagents. For every such a request there should be a prompt example the main agent calls a subagent. Such prompts must allow  the main agent add details regarding current problem that is being addressed, for example not just "analyze current code", but more detailed "analyze code to find how does it do: A, B, C; whether it has issues: E, F, G; provide response in a shape of <example of expected response>" etc, so the work of a sub-agent was more precise, like a cut of a surgeon, not a butcher, and the answer a sub-agent provides are actually helpful for crafting the plan to solve the problem we want to be solved by implementation of that plan.

4. Always ask questions if the decision plan is not linear and options significantly affect the final outcome. There is still a certain degree of freedom for the planning agent, and if the agent makes some assumptions and chooses directions to follow, this choices must be listed both in the draft of the plan, and in the final plan as a first block, before actual plan steps, so following steps were more clear, or if these assumptions are wrong, that can be seen from the beginning. The questions agent asks the use must have options to choose from, and brief explanations on how each of choices affect the following plan, with pros-cons, trade-offs; which option looks more favorable form agents point of view and why.

5. If there are certain skills, that can be used to create the better plan - they must be used. 

6. If there are certain skills, that can be used _during_ the implementation of the plan - they must be clearly stated in the plan. For example if plan includes writing tests and there is a skill for writing tests - it must be written in the plan to use that exact skill when writing tests. The same for an other task: if there is a skill - it must be used. 

7. After data is collected, tasks and current state is explored  understood, the user was asked important clarifications, the planning agent must draft the plan and remember to add choises and decisions as a first block. The plan itself must contain a high-level part (we do A, B, C), and  a low-level more detailed part after, where  in low-level plan each of steps is detailed into sub-sections, with notes on implementations, design decisions, important things to address, formulas if any needed, how initial problem was addressed here, discovered during exploration knowledge was accounted, etc.

8. Then priorities sub-agents evaluate the draft of the plan analyze it and provide their feedback to the planning agent. After all feedback is collected, the planning agent corrects the plan and provides the user the final version of the plan.

9. The final version also has <decisions made; assumptions assumed>, <high-level plan>, <low-level plan>
